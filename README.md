# Поиск квартир

Следит за объявлениями об аренде квартир на [kleinanzeigen.de](https://www.kleinanzeigen.de/),
[immowelt.de](https://www.immowelt.de/), [wg-gesucht.de](https://www.wg-gesucht.de/) и
[immoportal.com](https://www.immoportal.com/) по шести городам NRW
(Mülheim an der Ruhr, Wuppertal, Moers, Neukirchen-Vluyn, Gladbeck,
Bottrop — список сужен по просьбе пользователя, раньше следил за 12) и
шлёт в Telegram новые объявления, которые укладываются в лимиты по цене
и площади, допустимые джобцентром для одного человека.

Quoka.de пробовали подключать пятым источником, но отказались — общая
площадка объявлений с невалидным JSON, объявления часто без фото и низкого
качества по сравнению с остальными сайтами.

## Логика фильтра

1. **Площадь** — не больше `MAX_WOHNFLAECHE_QM` (по умолчанию 55 м²: 50 —
   норма, до 55 — согласованный запас).
2. **Цена** — сравнивается только **Kaltmiete** (холодная аренда, без
   коммунальных). У каждого объявления на Kleinanzeigen эта цифра доступна
   по-разному:
   - иногда указана прямо (поле «Kaltmiete» в характеристиках объявления);
   - иногда объявление даёт только «Warmmiete» и «Nebenkosten» отдельно —
     тогда Kaltmiete = Warmmiete − Nebenkosten;
   - иногда (особенно у комнат в WG) указана только «Warmmiete» без
     разбивки — точную Kaltmiete в этом случае посчитать нельзя, и такое
     объявление не попадает в уведомления (но не теряется — сохраняется в
     базе как просмотренное, чтобы не проверять его повторно).

   Логика реализована в `scraper.compute_kaltmiete()` и покрыта тестами в
   `tests/test_scraper.py`.
3. Итоговая Kaltmiete сравнивается с лимитом города (`max_kaltmiete` в
   `config.py`).

джобцентра/города, ответственного за каждый город. Площадь для 1 человека
везде принята за 50 м².

**По договорённости с пользователем фильтр сравнивает Kaltmiete именно с
этими цифрами напрямую** (без добавления Nebenkosten сверху) — это немного
строже официального правила (там Nebenkosten входят в лимит), то есть
скорее пропустит меньше вариантов, чем больше.

## Как работает поиск на Kleinanzeigen

Проверено вручную (см. `config.py`, `scraper.py`): фильтрация по городу
работает через query-параметры `locationStr` и `radius`, а не через слаг в
пути URL (слаг без верного внутреннего ID локации сайт молча игнорирует и
отдаёт объявления со всей Германии). Пример рабочего URL:

```
https://www.kleinanzeigen.de/s-wohnung-mieten/preis:0:880/c203?locationStr=Köln&radius=0&sortingField=SORTING_DATE
```

Бот на каждом цикле проверки:
1. Загружает первую страницу поиска (отсортированную по дате, новые
   сверху) для каждого города, с ценой в URL — с запасом
   `SEARCH_PRICE_BUFFER` от лимита, потому что в шапке объявления
   Kleinanzeigen иногда показывает Warmmiete вместо Kaltmiete (она выше).
2. Для объявлений, которых ещё не было в базе (`listings.db`), открывает
   страницу самого объявления и считает точную Kaltmiete и площадь.
3. Если Kaltmiete ≤ лимита города и площадь ≤ `MAX_WOHNFLAECHE_QM` — шлёт
   уведомление в Telegram со ссылкой на объявление.
4. Объявление помечается как просмотренное независимо от результата — при
   следующей проверке оно уже не откроется повторно.

## Как работает поиск на Immowelt

Immowelt закрывает страницу конкретного объявления (`/expose/...`)
капчёй DataDome — обычные HTTP-запросы туда не проходят (проверено, в том
числе с имитацией браузера через `curl_cffi`, обходить эту защиту не стали
осознанно). Сама страница поиска при этом открыта и без JS отдаёт реальные
объявления. Из-за этого у Immowelt другая, более простая, но и менее точная
схема, чем у Kleinanzeigen (см. `immowelt.py`):

- Цена, площадь и число комнат берутся прямо из атрибута `title` карточки
  в выдаче поиска (например: `Wohnung zur Miete - Nippes - 1.447 € - 3
  Zimmer, 96,3 m², frei ab 17.08.2026`) — заход на страницу объявления не
  требуется вообще.
- **Цена не проверяется индивидуально на Kaltmiete/Warmmiete**, как для
  Kleinanzeigen (страница объявления недоступна) — берётся как есть. У
  профессиональных площадок вроде Immowelt в выдаче по умолчанию показывают
  именно Kaltmiete, но это не подтверждено на 100% для каждого объявления.
  В уведомлении об этом всегда есть пометка «не проверено индивидуально».
- URL для фильтрации по городу — простой слаг в пути
  (`/liste/{slug}/wohnungen/mieten`), проверен вручную для всех 6 городов на
  отсутствие путаницы с одноимёнными районами (в отличие от Kleinanzeigen,
  тут с "muelheim-an-der-ruhr" всё чисто).
- Не нашлось рабочих query-параметров для фильтра по цене или сортировки
  по дате — сайт всегда отдаёт первую страницу с объявлениями по
  умолчанию (~40-50 штук на страницу). Отбор по цене/площади происходит
  уже на своей стороне, после разбора HTML.

## Как работает поиск на WG-Gesucht

WG-Gesucht отдаёт и страницу поиска, и страницу конкретного объявления без
какой-либо защиты от ботов - никаких капч, в отличие от Immowelt (см.
`wg_gesucht.py`):

- Фильтрация по городу — через числовой `city_id` в пути URL
  (`/wohnungen-in-{slug}.{city_id}.2.1.0.html`, `.2.` - категория «целые
  квартиры», не WG-комнаты), проверено вручную по `<title>` страницы для
  всех 6 городов, включая Mülheim an der Ruhr (там, где у Kleinanzeigen и
  Quoka была путаница с районами/соседними городами, тут всё чисто).
- На странице объявления — чистая пара «Miete: 1200€» / «Nebenkosten:
  450€» (Miete = Kaltmiete, проверено: Miete + Nebenkosten совпадает с
  Gesamtmiete/Warmmiete в шапке объявления), без Kleinanzeigen-style
  неоднозначности с Warmmiete-без-разбивки.
- Есть доступ к тексту описания объявления — фильтр по отказу от
  Bürgergeld работает так же, как для Kleinanzeigen.

## Как работает поиск на Immoportal

Immoportal - тоже без защиты от ботов, а цена и площадь подписаны прямо в
карточке выдачи поиска словами «Kaltmiete»/«Wohnfläche» - надёжнее, чем у
Immowelt, где цена вообще никак не подписана (см. `immoportal.py`):

- Фильтрация по городу — слаг в пути URL
  (`/suche/de/nordrhein-westfalen/{slug}/wohnungen/mieten`), проверен
  вручную по `<title>` для всех 6 городов, включая Mülheim an der Ruhr.
- Заход на страницу объявления не требуется вообще — цена/площадь/фото
  уже есть в самой выдаче. Из-за этого (пока) нет фильтра по отказу от
  Bürgergeld для этого источника — понадобился бы отдельный поход на
  страницу объявления только ради текста описания.

### Дополнительные фильтры (кроме Tauschwohnung)

Найдены при живом тестировании и реализованы в `filters.py`, применяются
везде, где есть доступ к нужному тексту:

- **Bürgergeld-отказ** — некоторые арендодатели прямо пишут в описании
  «Bürgergeldempfänger nicht gewünscht» (в любом порядке слов — «kein
  Bürgergeld» или «Bürgergeld ... nicht gewünscht»). Такое объявление
  пользователю всё равно недоступно, отсеивается. Работает для
  Kleinanzeigen и WG-Gesucht (текст описания со страницы объявления) —
  для Immowelt недоступно из-за капчи на странице объявления.
- **Monteurwohnung** — посуточное жильё для командированных рабочих
  («Ferien-Monteur», «Monteurzimmer» и т.п.), цена в объявлении не
  помесячная Kaltmiete, а посуточная — отсеивается по названию.
- **Zwischenmiete** — временная субаренда на несколько недель/месяцев с
  чётким сроком окончания, не долгосрочная аренда — отсеивается по
  названию (реальный пример: 2 из 5 объявлений на WG-Gesucht оказались
  такими).
- **Встречный поиск** — заголовки вида «Rentnerehepaar sucht schöne
  Wohnung» (кто-то ищет квартиру, а не сдаёт) отсеиваются по слову
  «sucht» в заголовке. «gesucht» не трогаем — это обычная формулировка
  предложений вроде «Nachmieter gesucht» («ищем нового жильца» = сдают).

## Установка

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
```

## Настройка (.env)

Скопировать `.env.example` в `.env` и заполнить:

1. **BOT_TOKEN** — создать бота через [@BotFather](https://t.me/BotFather),
   команда `/newbot`. Этот бот только шлёт уведомления.
2. **CHAT_ID** — написать что-нибудь новому боту, затем открыть в браузере
   `https://api.telegram.org/bot<TOKEN>/getUpdates` и взять
   `message.chat.id` из ответа.
3. **GITHUB_TOKEN** (необязательно) — classic PAT с правами `repo`, нужен
   только для синхронизации с облаком (см. раздел выше). Без него
   локальный бот работает как раньше, но независимо от облачного.
4. Остальные параметры (периодичность проверки, макс. площадь, радиус
   поиска, буфер цены) — по умолчанию разумные, менять не обязательно.

Города и лимиты цены заданы прямо в `config.py` (список `CITIES`) — их
можно поправить там же, если лимит для какого-то города обновился.

## Запуск

```
.venv\Scripts\python main.py
```

Дальше бот раз в `POLL_INTERVAL_MINUTES` минут (по умолчанию 15) проверяет
все шесть городов на всех четырёх сайтах и шлёт уведомления в чат с ботом.

Кроме локального запуска, тот же код работает в облаке через GitHub
Actions (`.github/workflows/check.yml`, запуск `run_once.py`) — раз в ~15
минут, независимо от того, включён ли домашний компьютер. Состояние там
хранится в `cloud_seen.json`, отдельно от локального `listings.db`.

### Про надёжность расписания GitHub Actions

Cron стоит на `7,22,37,52 * * * *`, а не `*/15` (0/15/30/45) - специально.
GitHub прямо предупреждает, что круглые отметки каждого часа — пиковая
нагрузка на scheduler у всех репозиториев разом, и `schedule`-триггеры там
задерживаются сильнее всего. На практике разрыв между реальными прогонами
дорастал до **11 часов** (2026-08-27/28, видно по `gh run list`) при
`*/15` — за это время локальный бот (если ПК был включён) находил объявления,
а облако — нет, что выглядело как "облако не работает", хотя сам workflow
всегда завершался `success`, просто GitHub слишком долго не ставил его в
очередь. Если после смещения минут задержки всё равно большие — стоит ещё
проверить, не исчерпан ли лимит бесплатных минут Actions на странице
биллинга GitHub (для приватных репозиториев он ограничен).

### Синхронизация локального бота с облаком

Раз локальный и облачный боты работают параллельно и независимо, без
синхронизации одно и то же объявление можно получить дважды — сначала от
облака (пока ПК был выключен), потом ещё раз от локального бота, когда он
увидел то же объявление как "новое" для своей отдельной базы. Чтобы этого
не было, `sync.py` перед каждым циклом подтягивает `cloud_seen.json` через
GitHub Contents API (без `git pull`/`git reset`, чтобы не трогать рабочую
копию репозитория — там же может идти обычная разработка) и помечает эти
id как уже просмотренные локально, а после цикла отправляет туда id,
которые нашёл сам, но которых там ещё нет.

`run_once.py` (облачный workflow) делает то же самое через тот же
`sync.push_new_ids` — раньше он коммитил `cloud_seen.json` напрямую через
`git commit && git push` внутри `check.yml`, и это реально ловило гонку с
локальным ботом (`git push` падал с "rejected (fetch first)", если оба
писали примерно в одно и то же время — см. 2026-08-24). Теперь оба
писателя используют один и тот же безопасный путь: конфликт разрешается
через `sha` содержимого файла — API отклоняет устаревший `sha`, и
`push_new_ids` просто повторяет попытку с актуальным состоянием (до 3
раз), без риска сломанного git rebase на минифицированном
однострочном JSON.

Нужен `GITHUB_TOKEN` в `.env` (classic PAT с правами `repo`) — без него
синхронизация просто выключена, и оба бота работают как раньше, независимо.

### Самопроверка источников

Kleinanzeigen 2026-08-19 незаметно сменил вёрстку карточек в выдаче поиска,
из-за чего парсер несколько дней молча возвращал 0 объявлений для 9 из 10
городов (кроме первого в списке) — без единой ошибки в логе. Чтобы такое
не повторилось незамеченным ни на одном из сайтов, каждый цикл `main.py`
дополнительно проверяет сырую выдачу по трём городам для всех четырёх
источников (`_check_source_health`, список в `_HEALTH_CHECK_SOURCES`);
если конкретный источник вернул 0 объявлений по всем трём — это шлёт
отдельное предупреждение в Telegram с именем источника (один раз, пока не
восстановится — у каждого сайта свой флаг, поломка одного не маскирует и
не путается с состоянием остальных) и пишет в лог с меткой `[health]`.
Работает только локально, встроено прямо в бесконечный цикл бота — не
зависит ни от какой сессии Claude Code и не ограничено по времени, в
отличие от cron-задач внутри сессии.

### Проверка самого BOT_TOKEN

Отдельная и более коварная поломка случилась 2026-08-28/29: при правке
секретов в GitHub через PowerShell в начало `BOT_TOKEN` затесался невидимый
BOM-символ. Токен стал невалидным, каждая отправка в Telegram из облака
падала с `404`, но сам `run_once.py` ловил эту ошибку внутри `_run_check` и
workflow всё равно репортил `success` — почти сутки никто не заметил, что
уведомления не доходят, потому что не было явного сигнала о поломке. Локальная
самопроверка (`_check_source_health`) это тоже не поймала: она проверяет
только "сайты отдают объявления", а не "Telegram реально принимает
сообщения", и вдобавок работает только в `main.py`, а сломан был именно
облачный секрет, до которого локальный бот вообще не достаёт.

Исправлено так:
- `notifier.verify_bot_token()` — лёгкая проверка через Telegram `getMe`
  (без отправки сообщения в чат), вызывается в начале каждого прогона.
- В `run_once.py` (облако) невалидный токен **роняет весь workflow**
  (проброс исключения наружу) — это даёт настоящий внешний сигнал,
  видимый прямо в `gh run list` (`failure`, а не `success`), без
  необходимости лезть в лог.
- В `main.py` (локальный бесконечный цикл) невалидный токен не роняет
  процесс (это было бы хуже — бот бы просто умер), а пишет отдельную
  ERROR-запись в лог каждый цикл — Telegram-алерт тут послать физически
  нельзя, это же он и сломан.

## Структура

- `models.py` — модель `City` (без зависимости от `.env`, чтобы её могли
  импортировать `scraper.py`/`tracker.py` без настроенного окружения)
- `config.py` — чтение настроек из `.env`, список городов и их лимитов
- `scraper.py` — поиск объявлений на Kleinanzeigen, разбор карточки
  объявления, расчёт Kaltmiete
- `immowelt.py` — поиск объявлений на Immowelt, разбор цены/площади прямо
  из выдачи поиска (страница объявления недоступна из-за капчи)
- `wg_gesucht.py` — поиск объявлений на WG-Gesucht, разбор карточки
  объявления, расчёт Kaltmiete (чистая пара Miete/Nebenkosten, без защиты
  от ботов)
- `immoportal.py` — поиск объявлений на Immoportal, цена/площадь прямо из
  выдачи поиска (явно подписаны, без защиты от ботов)
- `filters.py` — общие фильтры-исключения (Tauschwohnung, Monteurwohnung,
  Zwischenmiete, встречный поиск, отказ от Bürgergeld) — используются
  `tracker.py` для всех источников
- `storage.py` — SQLite: какие объявления уже видели (`listings.db`,
  используется локальным `main.py`)
- `storage_json.py` — то же самое, но в виде JSON-файла вместо SQLite —
  используется `run_once.py` в GitHub Actions, где нет постоянного диска
  между запусками
- `sync.py` — синхронизация "уже видел" между локальным ботом и облаком
  через GitHub Contents API (см. раздел "Синхронизация..." выше)
- `tracker.py` — логика одной проверки города по каждому из двух сайтов:
  найти новые объявления, отфильтровать, отправить уведомления
- `notifier.py` — отправка сообщения через Telegram Bot API
- `logger.py` — настройка ротируемого лога (`bot.log`)
- `errors.py` — классификация ошибок (временная сетевая / реальная)
- `main.py` — бесконечный цикл опроса всех городов (локальный запуск)
- `run_once.py` — один проход по всем городам и выход (для GitHub Actions)
- `.github/workflows/check.yml` — расписание облачного запуска
- `tests/` — юнит-тесты (расчёт Kaltmiete, дедупликация, фильтрация)

## Тесты

```
.venv\Scripts\pip install -r requirements-dev.txt
.venv\Scripts\python -m pytest
```

Покрыто: разбор характеристик объявления и расчёт Kaltmiete по всем трём
сценариям (`scraper.py`), разбор карточек в выдаче поиска с реальной
разметкой Kleinanzeigen, дедупликация по `ad_id` (`storage.py`), вся логика
одной проверки города — совпадение по цене/площади, отсев неподходящих,
объявления без точной Kaltmiete, повторный пропуск уже виденных
(`tracker.py`) — с лёгкими заглушками вместо реальных HTTP-запросов и
Telegram.

## Логи

`bot.log` рядом с проектом, ротация раз в сутки, хранится
`LOG_RETENTION_DAYS` дней (по умолчанию 14). `INFO` — какие объявления
найдены и отправлены, `WARNING` — временная сетевая проблема (само
пройдёт на следующем цикле), `ERROR` — что-то реально сломалось, с
traceback.
